# Design

## Context

现有仓库已经有统一目录约定、软链接安装方式、脚本测试和独立作者指南，但 Skill 行为评估仍以少量手工案例为主，且不同 Skill 的测试结构不一致。当前变更只设计治理流程和评测资产，不在规划阶段重写现有 Skill。

## Goals / Non-Goals

**Goals:**

- 先为 `obsidian-rag` 建立可复用的行为审计和评测结构。
- 让触发边界、正例、负例、holdout 和回归案例可被单独审阅。
- 将 Skill 的通用行为、实现细节和外部事实分层维护。
- 以 OpenSpec 变更作为本次优化的计划、实施和归档边界，并将生成的 OpenSpec 工作流文件和变更文档作为仓库资产提交。

**Non-Goals:**

- 不在本次规划中替换 MCP、数据源、脚本实现或运行平台。
- 不把所有聊天记录自动转换为 Skill 规则。
- 不为了满足评测而添加无法由真实任务支持的规则。
- 不把个人展示偏好提升为跨场景的通用行为，除非它被明确确认并有覆盖案例。

## Decisions

### 以 `skill-quality-governance` 作为仓库级能力

选择建立一个统一治理能力，但本次只在 `obsidian-rag` 上落地。不同 Skill 的任务类型不同，但触发测试、反例、holdout、回归和变更记录的质量要求可以复用。

备选方案是只修改各个 `SKILL.md`，但这会把方法论分散到具体实现中，未来 Agent 难以判断哪些规则是仓库级要求。

### 先评测再修改

先为 `obsidian-rag` 建立旧版基线和案例矩阵，再决定哪些内容需要删除、拆分或重写。这样可以避免 Agent 用刚刚修改过的 Skill 解释修改后的结果，也能保留可比较的旧版本。

本次不建立“无 Skill”对照，以控制范围；后续如需证明 Skill 的绝对增益，再单独增加基线。直接根据已有人工印象重写 Skill 仍不被采用，因为无法区分真实改善与单案例过拟合。

### 只移动明显容易过期的内容

不进行大规模拆分。只有明显依赖当前路径、索引命令、运行环境或实现细节的内容才考虑移出 `SKILL.md`；核心检索策略、引用规则和完成条件继续留在主 Skill 中。

### 区分默认实现与不可变约束

默认输出格式、默认目录或默认展示策略可以作为当前通用实现，但必须明确它们是可替换默认值。只有影响正确性、安全性、兼容性或用户明确要求的内容，才应写成不可变约束。

### 保持两类测试分离

脚本单元测试继续验证确定性代码；Skill eval 验证从用户请求到工具选择、流程执行和最终行为的完整链路。两者互相补充，不用其中一种替代另一种。

### 使用渐进式披露而非继续扩充主文件

主 `SKILL.md` 只保留触发相关的核心流程、边界和完成条件。数据源细节、平台差异和操作参考按分支进入 `references/`；重复机械操作进入 `scripts/`。

## Risks / Trade-offs

- [评测成本增加] → 先为最重要、最容易误触发或有副作用的 Skill 建立小型测试集，再扩展规模。
- [测试案例本身过拟合] → 使用不同措辞、不同输入形态和独立 holdout，避免把测试句子直接写进规则。
- [规划文档变得过重] → OpenSpec 只记录本次变更的决策和任务，长期通用规则归档到正式 specs 和作者指南。
- [个人偏好与通用行为混淆] → 在每条候选规则中记录来源、适用范围和非目标，未经验证的偏好留在候选记录中。
- [工具实现漂移] → 将接口和路径事实留在代码、配置或命令帮助中，Skill 只描述如何选择和使用它们。
